# Incoming WhatsApp Inbox

The Operation workspace now has a **WhatsApp Inbox** shortcut to `/app/whatsapp-inbox`. This is a logged-in Frappe Desk Page built with page-local HTML/JavaScript/CSS, using the existing WhatsApp Message records. No extra message or conversation DocTypes, packages, sending endpoints, composer, new-chat action or read/unread tracking are introduced.

## Accounts and navigation

The single readable account opens automatically. With several accounts, each fresh page opening uses the accessible **WhatsApp Settings → Default Incoming Account**. A synthetic account previously viewed in the cached page never overrides that default. If there is no readable default, the user chooses an account first. The bottom-left avatar/account button switches accounts without changing defaults or configuration. Each switch clears old chat state and changes the real-time subscription. Inactive readable accounts remain available for historical browsing.

The left pane lists incoming conversations grouped by receiving account and normalized sender, most recently stored first. Rows show sender name/number, latest preview, time and sender type. Search matches normalized phone, WhatsApp profile name and registered names, never message bodies. Filters are All, Salespersons, Clients and Unknown; ambiguous matches are included in Unknown rather than assigned arbitrarily. The header identifies the sender separately from any ordering customer. Matching reuses the configured default calling code and exact normalized phone rules.

The right pane shows incoming-only chronological history, day separators, reply quotes, timestamps, private attachment previews, audio players and location maps. Unavailable media stays visible with a warning. Provider-shaped media JSON, hashes and signed CDN URLs are not presented as message text; actual captions and literal JSON text messages remain intact. Contact payloads become readable names/phones. A batched envelope selects the stored provider message ID, never another message's caption. Image thumbnails and first-page PDF covers are generated once from existing local files and stored as private source-owned File records. The lazy preview endpoint checks account, sender, source and File permissions; changed source content gets a different cache key. Size/pixel/time/resource limits bound rendering. PDF covers use existing `pdftoppm`; if unavailable, original downloads remain usable. Native audio controls use preload=none and never autoplay. Location cards use Frappe’s existing OpenStreetMap tile provider (approved by the user) with a marker and an explicit Open map link. No media is downloaded from Meta by this viewer. On narrow screens, list and chat become separate views with a Back action.

Both panes use viewport DOM virtualization, retaining only visible rows plus overscan. Server cursor pagination fetches conversations and history incrementally; fetched data can remain in page memory, but offscreen rows are unmounted. Variable message heights preserve a keyed visible anchor as previews load. A fresh chat opens at the latest messages.

Replies quote the stored original and can jump to a surrounding bounded history window. An unavailable original is explicitly labelled; it cannot be recovered from a provider ID alone. Outgoing messages are available only as referenced quote context, never as incoming timeline rows. Reactions decorate their target and replace/remove prior reactions for the same actor, including reactions stored outside the current history page.

## Permissions and live updates

Owner, Admin, Order Coordinator and System Manager may open the Page; APIs also require actual WhatsApp Message read permission and receiving-account access. Frappe list permissions/User Permissions apply before grouping or pagination, and returned source records are checked. Private files retain ownership, path and read checks. Inaccessible default accounts are omitted from the response. The inbox does not navigate to the upstream message form, whose own onload behaviour can send read receipts.

Incoming saves publish `whatsapp_inbox_changed` only after commit, to the guarded WhatsApp Account document room. Events carry only the account and opaque local message name, not text, phone numbers, provider IDs or credentials. The message name allows targeted recovery when transactions commit out of creation order or an imported message is backdated. Internal media success/failure changes also notify the inbox. Account moves notify both old/new account rooms; deletion notifies the former room. No edit/delete capability is added to the viewer.

The client debounces events, refreshes the authorized list and revalidates loaded/changed messages in bounded batches. Creation/name keyset cursors load older history and drain newly stored messages without an application-wide scan in Python. Changed attachments replace existing bubbles; removed or newly inaccessible rows disappear. The reader stays at their scroll position, with **Jump to latest** when new messages arrive away from the bottom. Account/chat/search switches fence stale responses. Reconnect, focus/visibility and online events refresh missed changes; manual Refresh remains available. Page hide unsubscribes listeners and cancels timers.

## Installation

Page metadata and its roles are versioned under the app module. The Operation shortcut is in `fixtures/workspace.json`. The existing install/migrate setup adds the `whatsapp_inbox_history` index on type/account/creation/name. Normal app migration applies these on another server; no new Python package installation is required. PDF covers require a system `pdftoppm` executable on PATH; missing support falls back to the original attachment. Live updates require Frappe's standard Redis/Socket.IO services and deployment websocket routing. Local Page metadata, the shortcut and index were applied without replacing unrelated workspace customizations. Fresh-server deployment/load testing remains deferred.

## Alternate development-site refresh fix

The inbox uses same-origin Frappe calls; it does not hardcode web port 8000. The reported `localhost:8001` instance serves `kunal-intake.localhost`. It was started with direct Python without `DEV_SERVER=1`, so Desk attempted Socket.IO through the web origin rather than the configured socket service. Sharing port 9000 also maps the `localhost` namespace to the other default site.

Local startup is now recorded in bench-root `Procfile.intake`: its web process runs with `DEV_SERVER=1` on 8001, and its dedicated Socket.IO process runs with `FRAPPE_SITE=kunal-intake.localhost FRAPPE_SOCKETIO_PORT=9001`. The local site's `socketio_port` is 9001. Start with `honcho -f Procfile.intake start` from the bench after the shared Redis services are running. The original port-8000/default-site services stay unchanged.

A visible-only 15-second recovery refresh complements realtime. It avoids overlapping requests, pauses in hidden tabs and stops on navigation; returning to the tab refreshes immediately. This also covers unavailable sockets. The updated 32 inbox UI checks and all eight UI testfiles pass. The actual port-8001 browser showed new 15:53 incoming messages and local-only fixture insertion/removal without manual refresh. The temporary fixture was removed; actual messages were preserved.
